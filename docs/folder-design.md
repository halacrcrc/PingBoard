### 3.1 `AppConfig` 新增 `folders`

    pub struct AppConfig {

### 3.2 `FolderConfig`

    pub struct FolderConfig {
        pub id: u64,        // ⚠️ 与主机 id 数值上会重叠（各自从 1 递增），靠「不同字段、从不互比」保证安全；

### 3.3 `TargetConfig` 新增 `folder_id`

    pub struct TargetConfig {

        pub folder_id: Option<u64>,

### 3.4 零迁移保证

v1.1.9 写出的配置**无需任何迁移**：缺 `folders` → 空数组；缺 `folder_id` → `None`
→ 现有主机全部落在临时区，行为与 v1.1.9 逐字节一致。

## 四、两条必须守住的安全约束

### 4.1 孤儿主机必须回落，不得消失

若某主机的 `folder_id` 指向**不存在的**文件夹（手工编辑、文件夹被删而配置未同步等），
载入时**必须**把它回落为 `None`（临时区），**绝不能因此不加载该主机**。

> 这是项目历史上「主机列表全部清空」那类事故的同源风险。红线 R1 的教训：
> **宁可降级一个字段，也不要让整份配置反序列化失败。**

### 4.2 不得破坏 `AppConfig.targets` 的承重结构

`docs/HANDOFF.md` §5.2.1 记录了一条承重设计：
**「`targets` 数组里出现非对象元素」是当前唯一还能让整份配置解析失败、
从而触发备份+抢救的形态。**

- 不要给 `targets` 数组加「静默跳过非法元素」的容错 ——
  堵上它会让备份+提示的触发器消失，原文件在退出时被静默覆盖，**比现状更糟**，
  而且所有测试依然全绿（测试验的是「解析成功」，不是「有没有触发备份」）。
- `folders` 用 `deserialize_folders` **逐元素跳过非法项**（它不承担承重职责），
  这样「文件夹写坏了」不会连带影响主机列表 —— 这正是我们要的方向。

## 五、统计持久化

### 5.1 为何独立成文件，不塞进 `config.json`

1. **写入频率差异巨大**：配置只在增删改时写；统计每 500 ms 就变。混在一起会让配置频繁落盘。
2. **职责分离**：配置是「用户意图」，统计是「运行时数据」。清空统计 = 删一个文件，语义干净。
3. **有先例**：事件日志已单独落盘 `pingboard-events.jsonl`。

路径：`%APPDATA%\com.pingboard.desktop\pingboard-stats.json`

### 5.2 结构

    pub struct TargetStats {
        pub sent: u64,
        pub received: u64,
        pub failed: u64,
        pub sum_rtt_ms: f64,
        pub min_rtt_ms: Option<f64>,
        pub max_rtt_ms: Option<f64>,
        pub avg_rtt_ms: Option<f64>,
        pub last_rtt_ms: Option<f64>,
        pub ttl: Option<u32>,
        pub consecutive_fail: u32,
        pub loss_pct: f64,
        pub last_success_ts: Option<u64>,
        pub history: Vec<Option<f64>>,   // 趋势图完整保留（用户明确要求）
    }

    pub struct StatsFile {
        pub version: u32,
        pub saved_at: u64,
        /// key = 目标 id；目标已删除的条目在保存时剔除
        pub targets: HashMap<u64, TargetStats>,
    }

每字段同样带 serde 默认值；`history` 保存时按 `settings.history_len` 裁剪，
避免用户调小 `history_len` 后残留超长数组。

### 5.3 保存时机

| 时机 | 行为 |
|---|---|
| 应用退出前 | 保存 |
| 「停止全部」后 | 保存（用户常在这时关机） |
| 定期 30 s | 保存，防异常退出丢数据 |
| 「清空统计」 | **删除文件**（而非写空） |
| 目标被删除 | 从内存 Map 剔除，下次保存不再落盘 |

「清空统计」只清统计字段，**不动主机列表与文件夹归属**；清空后文件被删除，
重启不会「复活」旧统计。

## 七、界面

### 7.1 侧边栏（新增，宽约 200px，可折叠）

**多选 + 一个都不勾 = 全部**（单选只是多选的特例，**不维护两套逻辑**）：

    [x] 临时区   (3)      彩色圆点 + 名称 + 台数；复选框勾选
    [ ] 机房A   (12)
    [x]机房B    (8)
    [ ] 机房C    (5)
    [+ 新建文件夹]

- 勾选若干项 → 范围 = 它们的**并集**；**一个都不勾 → 范围 = 全部**
- 「临时区」= `folder_id = null` 的那一组，**可与文件夹混选**
- 各项支持右键：重命名 / 改颜色 / 删除
- 选中某范围 → 下方主表按该范围过滤；**主表 13 列布局与排序完全不动**
  （项目铁律：>=1200px 的视觉与行为是已验收基线，不得为新功能改动宽视口观感）

### 7.2 导出对话框的范围语义（v1.1.9 变更）

「范围」行改为：

    范围   [ 选中范围（N） ]  [ 仅勾选行（M） ]

- **「选中范围」** = 侧边栏当前勾选范围内的**全部**节点（不勾 = 全部节点）
- **「仅勾选行」** = 主表里用复选框勾中的行
- 术语避让：侧边栏勾的是**文件夹**，主表勾的是**行**，
  故用「选中范围」与「仅勾选行」区分，避免两个「勾选」混为一谈
- **与 v1.1.9 的差异**：v1.1.9 无侧边栏，「全部节点」= 全局全部。
  这是**新定义**（不构成兼容性破坏），但**必须补测试**锁住「跟随侧边栏范围」，
  防止以后被改回全局而不自知。
- 导出文件名**不带文件夹名**（范围可能是多个文件夹，名字会过长），
  仍只用筛选口径后缀：`pingboard-report-no-loss.csv` 等

### 7.3 添加主机 / 文件导入

两个入口都加「目标文件夹」下拉，默认「临时区」，可选任一文件夹或当场新建。

### 7.4 清空列表

只删 `folder_id = null` 的主机。有文件夹时，确认框文案必须明确说明
「将只清空临时区的 N 台，文件夹内的 IP 不受影响」。

## 十、兼容性冲突检查（新增功能 vs 既有功能/规则）

> 本节是硬要求：**任何新增功能都必须逐条对照既有规则过一遍**，确认不冲突、不破坏兼容性。
> 下面是本功能实际查出的冲突点与处置。

### C1 跨文件夹重复检测 —— ✅ 已定：维持全局判重

**现状**：添加主机的查重是**全局**的（`AddTargetsDialog` 的 `findDuplicateHosts`
与 `decideAdd()` 决策纯函数都按 host 全局判重）。

**冲突**：同一个 host（同一 IP）能不能同时存在于两个文件夹？
- 若**允许**：同一 IP 会被 ping 两遍 → **两份独立统计、两个线程**，
  丢包率/延迟数据分裂，用户无法判断哪个才是真实链路；也更容易撞 `max_threads` 上限。
- 若**禁止**：需在确认框里说明「该主机已在文件夹 X 中」，跨文件夹的批量导入会被拦下。

**✅ 已定**：维持**全局判重**（与 v1.1.9 规则一致，不引入新语义），
重复确认框文案补上「已存在于：<文件夹名>」。

### C2 导出对话框「全部节点」的含义 —— ✅ 已定：跟随侧边栏范围

**现状**：`ExportDialog` 收到的是 `snapshot.targets`（全局全部），
v1.1.9 的「全部节点」= 全局全部。

**冲突**：引入侧边栏后，用户在侧边栏选中「机房A」再打开导出对话框，
「全部节点」应指机房A 还是全局？

**建议**：让「全部节点」跟随侧边栏当前范围（侧边栏选了什么，导出对话框的
「全部节点」就是那个范围），这样「我正在看机房A，导出机房A的全部」符合直觉。
**注意**：v1.1.9 无侧边栏，因此这是新定义，不构成兼容性破坏。
但**必须补一条测试**锁住这个联动，避免以后改成全局。

### C3 「清空统计」与统计持久化的交互 —— 必须同步处理

**冲突**：`reset_stats` 若只清内存、不删 `pingboard-stats.json`，
**重启后旧统计会复活** —— 这违背用户对「清空」的预期。

**处置**：清空统计时**删除统计文件**（而非写空），并在 Rust 侧加测试锁定。

### C4 统计文件的结构演进需容错，且不得触发配置损坏提示

**冲突**：`AppConfig` 解析失败会触发「备份 + 抢救 + 弹提示」这条承重链路。
若 `pingboard-stats.json` 也走同一条链路，一个统计文件写坏就会弹
「配置文件已损坏」的误导提示。

**处置**：`stats.json` 解析失败**整体降级为空统计**（静默或日志），
**绝不**触发配置损坏提示。它不是配置文件。

### C5 搜索框、表头全选与文件夹筛选的叠加口径

**现状**：搜索过滤 `snapshot.targets`；表头全选「仅作用于当前搜索过滤后的可见列表」。

**冲突**：引入文件夹后，可见列表 = 搜索结果 ∩ 侧边栏范围。全选作用域要跟着变。

**处置**：过滤链固定为 `文件夹范围 ∩ 搜索关键词`，
全选作用于该链的结果。需补测试。

### C6 「删除选中」可能跨文件夹

**冲突**：勾选状态可跨文件夹；删除时提示只说「将删除 N 台」，
用户不知道其中有文件夹内的主机。

**处置**：删除确认框列出按文件夹分组的台数；不改变现有删除逻辑。

### C7 已有规则的复用（无冲突，确认可用）

| 既有能力 | 复用点 |
|---|---|
| `start_pinging(ids)` 已支持按 ids 启动 | 侧边栏「开始此文件夹」直接复用，无需新命令 |
| `reset_stats(ids)` 已支持按 ids 重置 | 「清空此文件夹统计」直接复用 |
| `export_targets(ids)` 已支持按 ids 取数 | 「导出此文件夹」直接复用 |
| `remove_targets(ids)` | 移动出文件夹 = 改 folder_id，不删除主机 |
| `export_report` 的 `filter` 参数 | 与文件夹**正交**，可叠加，不需改后端 |

### C8 与 UI 铁律的相容性（已确认无冲突）

- 侧边栏是**新增区域**，不改动主表 13 列布局 → 符合「≥1200px 观感是已验收基线」
- 侧边栏不隐藏任何既有功能入口 → 符合「功能入口不得隐藏或合并」
- 文件夹颜色用预设色板（浅/深两套已定） → 符合 WCAG AA 与「绿=正常红=失败」语义
- 侧边栏用 flex 居中/固定宽度，不依赖 getBoundingClientRect 定位
  → 天然规避缩放定位坑；若后续要用弹出菜单，**必须**除以 `currentZoomFactor()`

| 文件夹颜色 | 预设 8 色色板，浅/深两套；不用自由取色器 |
| 统计持久化粒度 | 连趋势 history 一起持久化 |

**设计已闭合，可直接开工。** 唯一需在实现中保持的纪律：
本节每个 ✅ 决策都要有对应测试锁住，否则以后被无意改回不会有人发现

### 3.5 文件夹 id 与主机 id 的关系（修正一处不准确描述）

**⚠️ 原设计稿写「与 target id 独立编号空间」，这不准确。**

实现中两者**数值上会重叠**（文件夹 id 与主机 id 各自从 1 开始递增）。
之所以安全，靠的是两条纪律而非数字区间隔离：

1. `folder_id` 与 `TargetState.id` 是**不同字段**，代码中**从不互相比较**。
   侧边栏渲染与筛选只经由 `folder_id` 走，不与 `id` 交叉。
2. **`0` 保留为临时区哨兵**（`folder_counts` 用 key `0` 代表「未分类」）。
   主机 id 从 1 开始、文件夹 id 也从 1 开始，故 **0 永不与任何真实 id 相等** ——
   这条是硬不变量，若破了会导致某台主机被永久算进临时区且无法移出。

> 这条不变量由 `qa_v110_folder_id_invariants` 锁定。
> **代码评审注意**：新增任何「某主机是否属于某文件夹」的逻辑时，
> 绝不可写成 `target.id == folder_id`。
