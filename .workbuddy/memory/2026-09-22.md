## BugFix：工具栏在选中主机后按钮文字折行（用户截图反馈）+ 两项提示能力

用户反馈：工具栏在选中 IP 后多出三个按钮，导致「添加主机」「清空统计」等文字被折成两行，观感差。
同时提问：「添加 IP 时单个网段限制了，多个网段累加有没有限制？」

### 先查清的事实（回答用户提问用）
- 单次批量 / 文件导入 / 单个 IP 段展开：前端 `MAX_BATCH = 1024` 上限（超出静默截断）
- **跨批次累加：没有任何上限** —— 后端 `state.rs:159 add_targets` 逐条 push，不计数、不查重
- 限制只在**启动 Ping** 时发生：`limit_max_threads=true`（默认）时总数 > `max_threads`（默认 256，可调 1..1024）
  直接拒绝启动并返回可读错误；关闭开关后仍保留 `state.rs:31 HARD_MAX_THREADS = 4096` 硬保护
- **跨批次重复添加同一 IP 不会去重**（`parseBatch` 的去重只在单次粘贴内部）

### 折行根因
工具栏根容器是 `flex items-center gap-2`（`h-12 shrink-0`，不换行），但**按钮上没有禁止内部文字折行** ——
flex 压缩时浏览器把按钮压扁、文字在按钮内部折行。

### 用户拍板的方案
1. ✅ 紧凑组合（不用"缩小字体"）：选中操作区由三个长按钮改为「已选 N ｜ 开始 停止 删除」一组
2. ✅ 加「累加超限」前端提示
3. ✅ 加「跨批次重复目标」检测 + 提交前二选一（跳过重复 / 仍然全部添加）
4. ❌ 否掉「窄视口把清空统计+清空列表合并为『清空 ▾』下拉」——「一键清空」是 v1.1.0 原始需求，

### 设计过程与关键结论
- 共做了 3 轮 12 个方案的手绘 SVG 草图，最后用户选定**雷达同心圆**方向。
- 用户中途要求「白底 + 最外环与图标边缘相切」，最后又改回「优化 A 的深色底 + 环相切」。
  深色底版已采用；白底版保留在 `docs/app-icon-alt-white.svg` + `.png`，一句话可换。
- **核心教训：图标必须先看 16/24/32px 效果再定稿。**
  - 细描边圆环（stroke 20–64）在 16px 下被抗锯齿**整圈吃掉**，只剩一个孤立的中心点。
  - 解法：**用实心环带（evenodd 双圆弧）代替细描边**，环带即使缩到 16px 仍可辨识。
  - 线宽换算：1024 画布上 stroke 100 ≈ 16px 时 1.56px，stroke 64 ≈ 1.0px（临界值）。
    **小尺寸下要可见，线宽至少 100（1024 坐标系）**。
- 相切的几何算法：圆角方形 40..984（边长 944，rx 200），
  中心 (512,512)，**外环外半径取 472（=944/2）即与四边中点相切**，
  且半径 472 的圆完全内切于该圆角方形（对角方向边界在 584.6，远大于 472）——无需裁切。
- 深色底上扇区硬边会在正上方形成一条竖缝 → 把扇区角度从 -92°~-28° 挪到
  -78°~-22°，避开垂直线。

### 复用的技术手法（已沉淀到技能 tauri2-windows-package-and-verify）
- **SVG 手绘图标 → Edge 无头渲染 PNG**：
  `msedge --headless=new --disable-gpu --hide-scrollbars --default-background-color=00000000 --force-device-scale-factor=1 --window-size=1024,1024 --screenshot=out.png file:///path.svg`
  （`--default-background-color=00000000` 是拿到**透明背景**的关键）
- **生成全套图标**：`npx tauri icon <1024.png> --output <dir>`（需 `NO_PROXY='*'`），
  一次产出 50 个文件（Windows ico 含 16/24/32/48/64/256，另有 icns / iOS / Android）
- **验证小尺寸的唯一可靠方式**：用 PIL 读 ico 的指定尺寸条目
  （`im = Image.open('icon.ico'); im.size = (16,16); im.load()`），再按最近邻放大 7 倍拼图目视。
  **不要只看 1024 源图就下结论**。
- 检查 ico 内嵌尺寸清单：Python 手动解析 ICONDIR（`struct.unpack("<HHH", head[:6])` 再循环 16 字节条目）

开始主机，也都没有内容，所以这个功能是干啥的」

## 根因定位（这才是问题本质）
事件**不在后端产生**，而是在前端 `App.tsx` 用前后两次快照 diff 生成，规则写死
「`ok` → 失败」记一条、「失败 → `ok`」记一条。而后端真实的状态迁移是
**`idle` → `resolving` → `failed`** —— 三条边沿规则全不命中：
- 「启动后就没连上」（`idle`→`resolving`→`failed`）不记
- 「DNS 解析失败」不记
- 只有「先通、后断」这一种情况能记到 —— 而这在用户测试里恰好没出现
另外 `LogEntry` 类型里定义了 `kind: "info"`，**全项目没有一处产出** —— 半成品。

## 方案（用户通过 AskUserQuestion 拍板）
- **三档等级 + 设置总开关**（`Fault` / `Standard` / `Detail`）
- 可选增强全选：**日志持久化**、**复制 / 导出**按钮、**条数 + 未读故障红点**、**保留条数可配**
- 用户补充：持久化也要开关；设置里加总开关；**主机详情页加单主机开关**；
  可调 Windows 资源管理器自选路径；**默认全部开着**
- 用户后续补充：「未读故障红点的两种呈现方式我想看下实际的图像再决定」→ 合成预览图后选 **A（标在主机列表行）**

## 三个关键设计决策
1. **打点位置挪到后端**（根因修复）—— 前端 diff 天生看不到「启动时就失败」这类迁移。
2. **`prev` 取「本轮循环开始、置 `Resolving` 之前」的状态** —— 工程师原本想用 `Resolving` 当 prev，
   我复核后确认必须用循环起点：否则**持久性 DNS 失败会每轮重复记一条**（241 台机器时事件会爆炸）。
3. **记录时全量入库，展示时按等级过滤** —— 等级只是视图过滤器，不丢数据。

## 观察项 → 缺陷 → 修复
### ① 未读故障红点永不显示（死代码）
「红点只画在当前选中主机的面板上」+「只有非选中主机才计未读、选中即清零」
→ 两条规则**互斥**，条件永远不成立。
用户选择方案 A：红点移到**主机列表行的备注名右侧**；详情面板那个恒为 0 的胶囊徽标直接删除。
（实现要点：`unreadIds` 必须 `React.useMemo`，否则每 500ms 快照重建 Set → 击穿 `TargetTable` 的 `React.memo`）

### ② 文案前缀重复：`解析失败：解析失败：不知道这样的主机。`
`state.rs` 构造的 resolve 错误已自带「解析失败：」，`events.rs` 又拼了一次。
修法 `e.strip_prefix("解析失败：").unwrap_or(e)`，并补 2 个回归测试。
